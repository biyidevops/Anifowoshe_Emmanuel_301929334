# Portfolio 5 Distributed and Cloud Database Exercise

## Current setup
The current NoSQL implementation for the Alliance Chemicals IT Procurement system uses a single MongoDB 8.0.38 Community Server running locally within an Ubuntu GitHub Codespace. The server accepts connections on `127.0.0.1` without port forwarding or authentication, storing data in a local `/workspaces/mongodb-data` folder. There is no clustering, replication, or cloud topology implemented; it is a standalone practice instance.

## Proposed replication
To ensure hardware event records (such as logging when a laptop is `assigned`) are not lost if a server fails, the system could be upgraded to a replica set ([MongoDB Replication](https://www.mongodb.com/docs/manual/replication/)). A standard production proposal involves three data-bearing, voting members placed in separate failure zones to ensure high availability. 

| Member | Starting role | Location |
| :--- | :--- | :--- |
| `mongo-node-1` | Primary | Lagos HQ Data Center |
| `mongo-node-2` | Secondary | Nairobi Branch Data Center |
| `mongo-node-3` | Secondary | Cloud Region (e.g., AWS af-south-1) |

All data writes go to the Primary, which copies the operations to the Secondaries.

## Failure and consistency
If the Lagos Primary fails, the remaining nodes hold an election to choose a new Primary ([Replica Set Elections](https://www.mongodb.com/docs/v8.0/core/replica-set-elections/)). During this brief election period, the replica set cannot accept new write operations. If network issues isolate a node so that a majority of voting members cannot communicate, no Primary can be elected, and the set becomes strictly read-only to prevent data conflicts.

To guarantee an event is permanently saved, the application should require a majority write acknowledgement (`w: "majority"`). This ensures the `assigned` event is confirmed on at least two nodes before telling the user it succeeded ([Write Concern](https://www.mongodb.com/docs/v8.0/reference/write-concern/)). Because Secondaries update asynchronously, a slight delay (replication lag) can occur before they reflect the newest events. Crucially, the core PostgreSQL database remains the authoritative source for actual hardware inventory rules; this MongoDB replica set only provides high availability for the event logs.

## Sharding and cloud deployment
Replication copies the same data to multiple servers for safety. Sharding splits the data across multiple servers to handle massive scale ([Sharding](https://www.mongodb.com/docs/manual/sharding/)). The small volume of hardware assignment events generated by Alliance Chemicals does not require sharding; a standard replica set provides ample capacity.

Moving this topology to a managed cloud service like MongoDB Atlas would provide built-in security features, including mandatory authentication, encryption at rest and in transit, and IP access restrictions. It also automates disaster recovery through continuous snapshots ([Backup and Restore](https://www.mongodb.com/docs/atlas/backup-restore-cluster/)). However, managed cloud deployments introduce recurring operational costs. Furthermore, it is a significant limitation that deploying MongoDB in the cloud does not replicate the relational PostgreSQL database or automatically synchronize the IT hardware rules between the two disparate database systems.
